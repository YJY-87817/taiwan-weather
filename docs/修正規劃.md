## A. 正確性

### A1. 鄉鎮沒有測站時取到不相干的測站

`WeatherRepository.kt:80-89` 的 `currentForPlace` 找不到該鄉鎮的測站時，會退而取 `firstOrNull { it.county == place.county }`，也就是回應清單裡該縣的第一筆。清單順序和距離無關，所以平地鄉鎮可能拿到同縣高山測站的氣溫。畫面只寫測站名稱，沒有說明它不在這個鄉鎮。

修正：

1. 預報回應的每個 `Location` 都有 `Latitude`、`Longitude`（見 `app/src/test/resources/hourly.json`）。把它解析出來當作鄉鎮座標。
2. 退到同縣測站時，改選離鄉鎮座標最近的一站，並填入 `distanceKm`。
3. 測站的 `GeoInfo.StationAltitude` 也在回應裡。距離相近時優先選海拔差距小的，或直接排除海拔差太多的測站；門檻需要用實際資料試過再定。
4. `CurrentCard` 在測站不屬於所選鄉鎮時，顯示測站所在鄉鎮和距離。

因為觀測和預報目前是平行載入，這個修正要讓選站等預報的座標回來，或另外保存一份鄉鎮座標。兩種做法都可以，前者改動較小。

測試：在 `WeatherRepositoryTest` 加「同縣有兩個測站時選近的那個」，以及 `CwaParsersTest` 加座標解析。

### A2. 驗證授權碼時的非預期例外會閃退

`WeatherViewModel.kt:62-79` 的 `saveApiKey` 只接 `HttpException` 和 `IOException`。如果氣象署回 200 但內容不是 JSON，轉換器會丟 `SerializationException`。這個呼叫是從 `WeatherScreen.kt:235` 的 `rememberCoroutineScope().launch` 發出的，沒有其他地方接，所以 App 會直接關閉。載入天氣的 `launchLoad` 有接所有 `Exception`，兩邊不一致。

修正：`saveApiKey` 加上 `catch (e: Exception)`，回傳「氣象署回應的內容無法讀取，請稍後再試」之類的訊息。

測試：`WeatherViewModelTest` 加一則驗證時丟 `IllegalStateException`、預期回傳錯誤訊息且不儲存。

### A3. 定位失敗後畫面狀態沒有還原

`WeatherViewModel.kt:124-151` 的 `launchLoad` 在開始載入時就把 `usesDeviceLocation` 設成 `true`，失敗時只更新訊息。結果是：

- 「目前位置」的 chip 維持選取，但標題和資料仍是原本手動選的地點。
- 之後按「更新」會再試一次定位，而不是更新畫面上那個地點。

手動選地點失敗時也有類似情況：標題已換成新地點，但 `PlaceStore` 仍是舊地點。

修正：載入前記下 `place`、`usesDeviceLocation`、`snapshot`，失敗時還原這三個欄位並保留錯誤訊息。

測試：現有的 `failedDeviceLocationKeepsTheChosenPlace` 補上對 `usesDeviceLocation` 和 `snapshot` 的檢查，另加一則「失敗後按更新會重新載入原地點」。

### A4. 預報查不到鄉鎮時沒有訊息

`parseHourly` 和 `parseDaily` 找不到 `LocationName` 相符的鄉鎮時回傳空清單，`WeatherScreen` 遇到空清單就不畫那個區塊。定位得到的鄉鎮名稱來自測站資料，如果和預報資料集的名稱不同，使用者只會看到少了兩個區塊。

修正：`WeatherSnapshot` 區分「沒有資料」和「讀不到」。最簡單的做法是讓兩個預報欄位可為 `null`，和 `alerts` 現在的做法一致，畫面上顯示「這個地點暫時沒有預報資料」。

### A5. 觀測失敗會讓整個畫面失敗

`WeatherRepository.kt:21-29` 和 `:44-61` 只有警特報容許失敗。觀測、逐時預報、每日預報任何一個失敗且沒有快取，整個 `loadForPlace` 就丟例外，其他已經拿到的資料也不顯示。

修正：授權失敗（401、403）照舊往外丟，讓畫面要求重新輸入授權碼。其餘失敗改成該區塊為 `null`，至少有一個區塊成功就顯示畫面。這項和 A4 用同一組可為 `null` 的欄位，建議一起做。

### A6. 氣溫趨勢圖橫軸失真

`WeatherScreen.kt:381` 用 `index * stepX` 等距排列各點。測試樣本 `hourly.json` 的溫度資料前 36 筆間隔 1 小時，之後 19 筆間隔 3 小時，所以圖的後半段被壓成實際時間的三分之一。

修正：`TemperatureChart` 改收時間和溫度，橫軸依時間比例計算。順便在圖下方標出日期分界，否則 3 天的曲線看不出哪一段是哪一天。

README 和畫面上的「逐時預報」也要改成符合實際的說法，例如「未來 3 天預報」。

## B. 穩健性

### B1. 驗證流程和選單狀態放在畫面層

- `WeatherScreen.kt:182-246`：驗證跑在對話框的 `rememberCoroutineScope`，輸入文字用 `remember`。旋轉螢幕會取消進行中的驗證並清空輸入。
- `MainActivity.kt:24`：`showPicker` 是 Activity 的欄位，旋轉後選單會關掉。
- `MainActivity.kt:53`：`hasApiKey` 在每次重組時讀 SharedPreferences，不是狀態的一部分。

修正：驗證移到 `viewModelScope`，把「驗證中」、錯誤訊息、`showPicker`、`hasApiKey` 放進 `WeatherUiState`；輸入文字改用 `rememberSaveable`。A2 的例外處理會跟著落在 ViewModel，建議 A2 和 B1 同一批做。

### B2. 快取的後備條件太窄

`CachedSource.kt:40-57`：

- HTTP 429（超過呼叫次數）被當成一般 4xx 往外丟，不會改用已儲存的資料。
- 回應解析失敗（`SerializationException`）同樣不會退回快取。
- 回應是 200 就寫入，沒有檢查內容。如果氣象署回了空的 `records`，會蓋掉原本可用的快取。這一點需確認實際會不會發生。

修正：429 和解析失敗比照 5xx 處理；寫入前確認 `records` 存在。

### B3. 定位

`FusedLocationProvider.kt:13-15`：

- `getCurrentLocation` 傳入的 `CancellationToken` 是 `null`，協程取消時定位請求不會跟著取消。
- 沒有自訂逾時，等待時間由 Play 服務決定。
- 後備的 `lastLocation` 沒有檢查時間，可能是很久以前在別處的位置。
- 沒有 Google Play 服務的手機會丟 `ApiException`，畫面顯示成「資料讀取失敗（ApiException）」。

修正：用 `CancellationTokenSource` 接上協程取消，加 `withTimeoutOrNull`（例如 15 秒），`lastLocation` 只接受一定時間內的結果，並把 `ApiException` 轉成 `LocationUnavailableException`。

另外，權限被拒絕時（`MainActivity.kt:26-33`）只會打開地點選單，沒有說明原因。補一行訊息即可。

### B4. 警特報內文的配對

`CwaParsers.kt:58-61` 的 `detailFor` 取第一則含相同 `phenomena` 的內文。`W-C0033-002` 的每個 hazard 都有 `affectedAreas.location`（見 `alerts_detail.json`），應該同時比對縣市，避免同一種現象有多則特報時配錯。

### B5. 用最近測站判定鄉鎮

`StationLookup.kt:24-40` 以最近測站的鄉鎮當作所在鄉鎮，在鄉鎮交界或測站稀疏的地區可能判到隔壁。

可行的改法：先用最近測站決定縣市，再用該縣預報資料集裡各鄉鎮的座標（A1 會解析）選最近的鄉鎮。這只是把「最近測站」換成「最近鄉鎮中心」，仍然不是真正的行政區界判定，面積大的鄉鎮還是可能有誤差。要完全正確需要內建鄉鎮界圖資，成本高，建議先不做。

## D. 流量與請求次數

- **D1：** 每次載入都下載完整的 `O-A0003-001`，手動地點沒有對應測站或使用定位時還要再下載完整的 `O-A0001-001`。可以用 API 的欄位篩選參數只取需要的氣象要素，並在記憶體裡保留幾分鐘（觀測資料本來就是 10 分鐘更新一次）。
- **D2：** 地點選單的鄉鎮清單是下載整個縣的 3 天溫度預報再取名稱（`WeatherRepository.kt:39-42`）。鄉鎮名稱很少變動，可以長期快取，或直接內建。
- **D3：** 「更新」沒有最短間隔，每按一次就是 5 到 6 個請求。可以在一分鐘內重複按時直接回應現有資料。
- **D4：** `WeatherRepository.kt:137` 每次驗證授權碼都建立新的 `OkHttpClient`。改成共用一個 client、只換授權碼。

## E. 文件、CI、測試

- **E1：** README 的建置指令只有 Windows 版。補上 macOS 和 Linux 的寫法（`./gradlew assembleDebug`），並寫明需要 JDK 17 以上。
- **E2：** `.github/workflows/ci.yml` 的 Action 用版本標籤而不是 commit SHA；同一個 PR 連續推送時舊的執行不會取消；lint 報告只在失敗時上傳。三項都是小調整。
- **E3：** 測試缺口：
  - `CwaApi` 的攔截器（授權碼有沒有加到網址上）沒有測試，可以用 MockWebServer。
  - `WeatherScreen` 和 `MainActivity` 的啟動流程沒有任何測試。
  - A1 到 A6 各項修正都要補對應的測試，已分別寫在上面。
- **E4：** README 已載明的現況，列在這裡備查：沒有正式版簽章和 release 設定；授權碼未加密。要上架或分享給更多人之前再處理。
